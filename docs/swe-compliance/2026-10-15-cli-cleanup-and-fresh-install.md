### Bootstrap issue and scope boundary

The cached public index is schema version 2 and contains `runtime:node`,
`runtime:python`, `binary:sqlite`, and `binary:ripgrep` as package-ID keys.
`src/commands/init.js` reads the obsolete nested kind/official structure and
collects failures without failing the command. The existing full suite does not
exercise this live registry boundary. `doctor --json` also returns human text;
the smoke evidence therefore treats that command as text, not a JSON contract.

Disposition: record an implementation obligation, rather than broaden this
cleanup/audit into a bootstrap rewrite. Owner: CLI maintainer; trigger: before
claiming complete new-user bootstrap or the next onboarding release. Closing
proof: schema-v2 bootstrap test, shared verified installer use, nonzero partial
failure, fresh-home successful provisioning on both hosts. No second downloader
should be introduced. Root docs explicitly disclose the current limitation.

Independent review also found a general-inventory failure: every
`list-after-install.log` contains `[]` despite successful TypeScript execution.
The listing path does not discover dynamic npm tools nested under
`binaries/npm/<package>`. Disposition: investigate/fix in the next onboarding
change; owner: CLI maintainer. Closing proof: install a dynamic npm tool,
assert its presence in general inventory, remove it, then assert its absence.
Both defects have executable semantic acceptance assertions in
`assert_fresh_install.py`; `bootstrap` and `inventory` checks each exited 1
against the primary public-package report. These supplement the subprocess
exit records, which by themselves cannot detect either defect.

Clean-state tests share OS binaries and a standalone supported Node runtime;
they do not prove new-account permissions, a fresh OS, Node 22, Linux, Windows,
provider authentication, authenticated stack operation, or daemon startup.
